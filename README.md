2.1 哪些问题你选择在这个系统中解决
2.1.1

将任务先持久化到 MySQL，避免进程异常导致任务直接丢失。

2.1.2

保证业务方重复提交时不会重复创建任务，即接收侧幂等。

2.1.3

支持下游接口配置（类型 / 协议）。

2.1.4

限流配置 / 指数退避重试。

2.2 哪些问题明确不解决
2.2.1

不保证 Exactly Once。

原因：因为 HTTP 网络原因，无法保证请求一定成功，所以只保证至少投递一次，重复消息靠幂等解决。

2.2.2

外部系统自身业务返回不解决。

原因：只判断 HTTP 是否成功，不关心错误码，明确系统职责。

2.2.3

第一版不考虑大流量。

原因：无明确流量要求，先减少系统复杂度。

2.3 你选择的通知投递语义是什么？

至少一次。

原因：同问题 2.2.1。

2.4 在外部系统失败或长期不可用的情况下，你的处理策略是什么？

失败分为 3 类：

可恢复失败：用退避重试解决。
不可恢复失败，如 404：不重试，用报警解决。
限流：做等待重试策略。

如果长期不可用，可进入指数退避策略、报警，等下游恢复后看业务要求是否进行回溯处理。

2.5 在 AI 的方案建议中，你认为哪些设计是“过度”的，并选择不采纳
2.5.1

AI 提出引入 MQ 进行流量削峰，不采纳，目前用 DB 流量在可控范围内。

2.5.2

Redis ZSet / 时间轮 / Delay Queue 实现重试，不采纳，太过复杂，直接用 DB 状态字段然后脚本重试。

2.5.3

Exactly Once 投递，不采纳，达到这种效果需要引入分布式事务。

2.6 如果这是一个第一版系统，未来流量或复杂度显著增长时，你会如何演进
2.6.1

增加 Worker 并发向下游投递。

2.6.2

Endpoint 隔离备份，提升可用性。

2.6.3

引入 MQ，消除流量高峰。

3. 关键工程决策与取舍
3.1

DB 持久化，可追溯，可归因。

3.2

支持同步 / 异步，减轻系统压力。

3.3

支持重试脚本，提高最终触达成功率。

3.4

支持下游 API 注册灵活配置，可复用，维护成本低。



## 运行与验证

需要 Go 1.26 和 MySQL 8.0。设置 MYSQL_DSN 后执行 go run .，默认监听 :8080。
数据库启动时执行增量迁移；0004 增加 lease_version 和 attempt_count。
升级前备份数据库，迁移期间停止旧版本写入，完成后再启动新版本。

- 通知 API 只保存任务并唤醒调度器，所有投递经过最多 10 个并发工作协程。
- 手动重试仅接受 FAILED 状态，其他状态返回 409；重置本轮失败预算，保留历史尝试编号。
- 相同 business/request_id 但 endpoint 或 payload 不同返回 409。
- 限流等待保留记录，但不消耗发送失败预算。
- /healthz 检查进程存活；/readyz 检查数据库连接和调度扫描状态。
- /metrics 返回 JSON：投递成功、失败、等待累计次数、尝试总耗时和各状态任务数。计数器重启后归零；积压统计查询数据库。
- 停机停止领取新任务，等待已领取的在途请求结束，再关闭数据库。单请求最长 300 秒，应配置足够的进程退出宽限期。
- 地址仅允许 HTTP(S)，内部地址仍可用。身份认证和共享限流不在本次范围内。

本地验证：go test ./... 和 go vet ./...。
设置 TEST_MYSQL_DSN（独立测试数据库，含 parseTime=true）后运行 go test ./sev/repository -run MySQL。
GitHub Actions 使用 MySQL 8.0 执行 go test -race ./...，验证真实数据库租约和事务回滚。
