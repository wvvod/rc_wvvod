  2.1 哪些问题你选择在这个系统中解决
     2.1.1 将任务先持久化到 MySQL，避免进程异常导致任务直接丢失
     2.1.2 保证业务方重复提交时不会重复创建任务，即接收侧幂等
     2.1.3 支持下游接口配置(类型/协议)
     2.1.4 限流配置/指数退避重试
  2.2 哪些问题明确不解决
     2.2.1 不保证 Exactly Once 原因 : 因为http网络原因，无法保证请求一定成功，所以只保证至少投递一次，重复消息靠幂等解决
     2.2.2 外部系统自身业务返回不解决 原因：只判断http是否成功，不关心错误码，明确系统职责
     2.2.3 第一版不考虑大流量 原因：无明确流量要求，先减少系统复杂度
  2.3 你选择的通知投递语义是什么？
      至少一次 原因：同问题2.2.1
  2.4 在外部系统失败或长期不可用的情况下，你的处理策略是什么？
      失败分为3类
      可恢复失败：用退避重试解决
      不可恢复失败，如404 ：不重试，用报警解决
      限流：做等待重试策略
      如果长期不可用，可进入指数退避策略,报警，等下游恢复后看业务要求是否进行回溯处理
  2.5 在ai的方案建议中，你认为哪些设计是过度的，并选择不采纳
    2.5.1 ai提出引入mq进行流量消峰 不采纳,目前用db流量在可控范围内
    2.5.2 Redis ZSet / 时间轮 / Delay Queue 实现重试 不采纳，太过复杂，直接用db状态字段然后脚本重试
    2.5.3 Exactly Once投递 不采纳，达到这种效果需要引入分布式事务

  2.6 如果这是一个第一版系统，未来流量增长或复杂度增长时，你会如何演进
      2.6.1 增加worker并发向下游投递
      2.6.2 Endpoint 隔离备份 提升可用性
      2.6.3 引入mq 消除流量高峰
3.关键工程决策与取舍
  3.1 db持久化，可追溯，可归因
  3.2 支持同步/异步，减轻系统压力
  3.3 支持重试脚本，提高最终触达成功率
  3.4 支持下游api注册灵活配置，可复用，维护成本低
